# Beekapoo development

Engine modules and cables remain in Rack. Collapsed module widgets live inside zero-size holders registered under their original engine IDs. Their original widgets keep stepping. Exposed controls use the original parameter quantities. Outputs retain their original engine endpoints; exposed inputs use the native attenuverter routes described below.

`BeekapooRackEdit.hpp` implements Edit subpatch. Editing unwraps originals into direct Rack children in a clear row four rows below Beekapoo. A nonmodal toolbar provides Done, Expose, and an optional read-only panel preview. The stock Rack handles movement, selection, keyboard shortcuts, browser placement and cables. New eligible modules join after the placement drag ends. Done recreates holders and restores zoom, offset and the previous visible selection. Only one editing target is active at a time.

`BeekapooLayout.hpp` is the pure responsive planner. It runs on resize/mapping changes. `layoutControls()` applies control-type or module-first ordering and visibility filters. Hiding controls does not alter engine connections. Small layouts keep tiny jacks and icon controls; labels are added as space permits.

`BeekapooPortLayout.hpp` fits the existing I/O sections using bounded grow/shrink rules. A lone output gets its own width allowance. Each cell chooses an attenuverter above or beside its jack, reserves caption space, and chooses the native small or normal Computerscare jack size. Normal and compact panels share the same placement code; labels fit independently of the panel's size tier. This runs only on layout changes. The approach borrows free-space allocation from [Flexbox](https://www.w3.org/TR/css-flexbox/#flexibility), without introducing a general packing solver.

`BeekapooPortable.hpp` serializes contained modules and internal cables when Rack requests JSON, not on the audio or UI tick. Imported/duplicated groups receive independent module and cable IDs, remapped exposure and visibility references, and child actions attached to the native duplicate/paste undo action. Normal full-patch loading still uses the existing engine modules. Missing dependencies fail open rather than binding another group's modules. Local duplication copies available per-module patch storage. Rack selection files do not bundle external assets.

The older proxy-based subview remains as an internal regression fixture; panel and context-menu editing use the native-rack session. Its container-swapping API is not used for the new editing path.

`computerscare-beekapoo` is the current slug. Hidden aliases support `computerscare-peekaboo` and `computerscare-patch-abstractor`. Expanders and nested groups are unsupported.

## Validation and renders

`BeekapooImportDialog.hpp` presents Audio and multi-Beek import choices as a centered modal with explicit confirm/cancel. It owns native keyboard selection while open so Rack's scene-level shortcuts cannot run first; closing restores the previous surviving focus. The backdrop consumes clicks without dismissing, and the choices scroll within a fixed viewport for larger lists.

`BeekapooPatchFile.hpp` exports an isolated standard Rack archive: `patch.json`, the wrapper, its children and internal cables, and only those modules' storage folders. It never saves or replaces the active patch. Import reads into a temporary directory, selects one wrapper or synthesizes a group for an ordinary patch/selection, then uses the native preset replacement transaction. `BeekapooPortable.hpp` reserves new IDs, stages assets, and restores JSON before native `onAdd`, so modules such as Phlooper can load their assets immediately. File imports never resolve missing cable endpoints or assets against modules in the current rack. Keep/Expose recognizes Core Audio 2/8/16 and stoermelder AUDIO-64. `BeekapooAudioImport.hpp` removes hardware modules before dependency loading. Capture channels become shared input mappings (`shared`, `label`, `targets`, `incoming`) on the owner; native bridge cables fan out one attenuated polyphonic signal. Direct playback exposes original outputs, deduplicating identical sources. Stacked playback and capture-to-playback paths use unity Fundamental 8vert channels, packed eight per module. The legacy audio-relay model remains registered for existing saved patches but is never created by new audio-interface conversion. Shared mapping identities and every destination/cable reference are remapped on portable import and duplication. Merge temporarily releases incoming stacks at their first destination, then restores shared mappings without duplicating the stacks. Eject materializes native fan-out or a single gain channel feeding all destinations; disconnected capture inputs materialize zero to retain audio silence.

`scripts/preview-module.sh beekapoo` builds an isolated runner using local Rack graphics libraries. It does not operate live Rack or vcvmon. `--no-build` skips the plugin build, and unchanged runners are reused. The former `peekaboo` command is an alias.

The fixture checks native JSON reload, legacy slugs, four-channel DSP, stable cable identities, free rack footprint, mappings, switch behavior, tooltips, grouping undo/redo, native browser return, real-rack editing, module adoption, viewport restoration, independent duplication and selection paste with undo/redo. It also renders 16 responsive layout cases and native editing screenshots into ignored `build/previews/beekapoo/`.

Keyboard and menu deletion include the contents in Rack’s native selection-delete transaction. Other programmatic removal queues contained-module cleanup for the scene hook after native bulk-deletion traversal. This avoids invalidating Rack's copied selection/module lists. Surviving children and their cables are removed with actions inserted into the native delete transaction; Undo restores the complete group. A restored owner cancels an unprocessed removal. End abstraction still releases the children without deleting them.

Expose draws bordered, translucent irregular rectangles over the original controls, green for mapped controls and yellow for hover. Overlays are visible only in Expose mode; the source controls draw normally beneath them. Mapped panel ports draw computerscare jacks, using small artwork at compact widths and standard large artwork otherwise. Outputs forward patching/tooltip events to their original endpoint; attenuated inputs forward them to the owner’s native route input. Source graphics and framebuffers are never reused or modified.

Preset imports use one history transaction for the host, contained modules and cables, including replacement of an existing group. Exposure changes use group history; automatic boundary exposure and state restoration do not add history entries. Creating a Beek from a selection also chooses default exposures using the count ranges in `BeekapooExposurePlan.hpp`, distributed across members by `BeekapooExposure.hpp`. Existing boundary ports remain mandatory, internally patched inputs are skipped, and momentary parameters are excluded. This runs once in the creation transaction, never on restore or layout. Native selection-menu hooks recognize the complete translated Rack menu and shortcuts, rather than intercepting unrelated Delete/Duplicate labels.

Rack dispatches patch-save callbacks to the original engine modules once; Beekapoo does not forward them again. Explicit duplication prepares contained patch storage before copying it. Cable plugs remain native Rack widgets, with weak references cached per cable to avoid repeated widget-tree searches.

Header artwork is separate from panel geometry. Edit `res/Beekapoo/computerscare-logo.svg` directly; the panel generator does not overwrite it. `scripts/generate-beekapoo-panel.py` generates `res/Beekapoo/title.svg`. Both assets fit their own header areas, so compact widths cannot reveal clipped remnants of the title. The preview fixture includes an 8–12 HP strip with eight parameters and one input/output, checking visibility, labels and control bounds.

Headers show only the full logo at 4–6 HP. Wider headers fit the single-line title beside the logo. Edit always shows its icon and the contained-module count, with the word Edit when space allows. Section frames fill the panel around fixed control grids, with independently warped perspective plaques that slightly overlap and leave small unpainted gaps. There is no separate panel background. Module IDs seed each instance’s corner, depth and slant variation so its artwork survives reload. Complete frame silhouettes fit inside the panel bounds, including the bottom I/O sides. Header and module-action sections span the full width; exposed I/O stays flush at the bottom. A shared compact action-strip layout keeps the two Wiggle and two Randomize buttons beside Edit/Eject. Initialize widgets, their two CV inputs, and the Wiggle Amount widget remain allocated but hidden. The four Wiggle/Randomize inputs plus Generate and Grow inputs are shown below their buttons. Wiggle Amount is adjustable through a native context-menu slider.

Exposed Randomize uses Rack’s base bounded parameter distribution, bypassing `randomizeEnabled` and custom randomize callbacks. Exposed Wiggle also ignores that flag. Both skip momentary switches. All Randomize still calls each original module’s native handler; All Wiggle retains per-parameter exclusions.

The public panel uses Edit and Eject. Edit unwraps original modules into Rack; Near/Far translates the complete layout without rearranging members, and reopening retains their saved positions. New-module capture is an independent, saved Inside/Outside preference. Legacy expansion helpers remain for older history and regression fixtures. Eject records release plus native owner removal in one history transaction; the empty owner destructor cannot delete released children. Action buttons copy callbacks before execution and clear their event target if the callback destroys the button.

Native bypass callbacks queue a UI-side child update because Rack holds its engine lock during the callback. The UI uses public `Engine::bypassModule` after the lock is released. Normal playback adds no child bypass scan; a bypassed group also catches new/restored members.

Front-panel patching and jack menus temporarily filter hidden native cable/plug widgets during event handling; engine cables are never removed by that filter. Disconnect uses a shared boundary/panel-cable policy for module and selection commands. Imports preflight models and identities, allocate all child IDs, remap the known `data.maps` moduleId/paramId schema, then load each child once through native engine locking. Failure removes staged children and restores the original host/group; native Undo/Redo remains safe. Other plugin-specific reference schemas are not rewritten.

The native multi-selection menu adds Create Beek-A-Poo for selections of two or more modules. Creation combines native ModuleAdd and GroupHistory in one transaction. The owner is staged clear of the selection, then placed near its freed position. Shared UI initialization and browser previews install the scene hook even without an existing Beekapoo instance; plugin init also installs it when a UI context is already available. The installation fast path is constant-time.

The summed CPU readout uses Rack’s unsupported `Module::meterBuffer/meterLength/meterIndex` getters through the isolated `BeekapooCpuMeter.cpp` adapter. Its header only declares the helper, so normal plugin files retain Rack’s PRIVATE compile guards. The adapter deliberately includes the internal Module header; GCC otherwise rejects calls that Clang only warns about. It reads the latest samples only when CPU meters are visible and does no additional DSP timing. Check this adapter against new Rack SDKs. The native module draw retains Rack’s host plot. Its footer is redrawn with the subpatch total on the left and host cost on the right; both readings share one font size and scale down together only when needed.

Randomization locks are `(module ID, parameter ID)` pairs; `-1` locks the whole module. Group snapshots save them, portable imports remap their module IDs, and membership changes prune stale entries. Randomize All skips locked modules; partially locked modules retain their native callback, with protected quantities restored inside the same engine lock through `BeekapooRandomLocks.hpp`. Initialize deliberately ignores these locks. The normal DSP path does no additional work.

New browser instances generate a weighted 3–11-module subpatch from their selected module set (the initial set is Fundamental). The standalone planner chooses required signal/gate wiring, three useful free modulation inputs, one output, and a few parameters; VCA Mix is an ordinary optional module, not a mandatory input adapter. Generated positions use actual widget widths without gaps. `res/programs/beekapoo-names.json` contains the naming corpus. Its 351 words span 18 categories, including the complete save-branch vocabulary: animals, birds, fish, bugs, trees, plants, food, objects, tools, parts, materials, fabrics, terrain, water, weather, buildings, verbs and fruit. Duplicate words appear only once; the save-branch list keeps its existing order and behavior. Weighted templates combine words, repetitions, optional numbers and separators. The `raw` definition picks unchanged vocabulary; `vowel` changes one vowel; `chunk` expands one letter, such as `b` to `bed`. The `word` definition weights these 14:3:2. Replacement pairs and weights are editable data using the shared template expander’s `mutate` function. Existing saved names are unchanged. Edit vocabulary, definitions or pattern weights without changing C++. No generation runs on the audio thread.

Generation is deferred until the browser’s native ModuleAdd history action exists, and contained actions join that transaction. Restored, pasted, duplicated, template-loaded and selection-created instances do not generate. User names live in module data, so native Undo/Redo, presets, duplication and portable files retain them. A nonempty name replaces the title artwork, including on the initial 90 px panel. Empty names retain the usual logo/title breakpoints.

`BeekapooParamLayout.hpp` identifies matching parameter names and numbered families. `BeekapooParamBlocks.hpp` packs those families into independent rectangular regions, with a shared caption and balanced rows/columns inside each. A bounded slicing-tree search considers horizontal and vertical combinations; small sets try all family boundaries. Spare space grows each region's controls independently, up to 64 px. By module adds an outer grouping level. Very dense panels fall back to the existing compact layout without dropping controls. The pure planner uses no Rack state and runs only on layout changes; parameter values and exterior cables do not affect placement. Gaps, size limits, search bounds and scoring live in the block planner. Native parameter interactions remain unchanged.

`BeekapooIdentity.hpp` derives five stable hashes: module types sorted by manufacturer/model including duplicate counts, the deduplicated type set, the counted set plus typed port-to-port wiring, the sorted manufacturer list with one entry per module, and its deduplicated manufacturer set. Bounded neighbourhood refinement and connected-component records distinguish duplicate instances without depending on Rack IDs or positions. Only internal connections participate; exterior cables do not change the drawing. A cheap snapshot gates structural recomputation on the UI thread; parameter values do not affect it. Title capitalization uses a separately salted counted-module hash: 34% lowercase, 32% uppercase, 32% title case, 2% deterministic mixed case. Case is applied to generated titles before header text fitting and does not alter the stored name. Custom titles bypass casing and automatic name replacement. External cables, resizing and frame timing do not affect it.

`BeekapooKnob.hpp` combines these hashes to select one of six narrow palettes and parameter-family profiles, sizes, aspect ratios and bevels. Half of the parameter-family profiles are circles. The module-type and manufacturer-set hashes choose shared plain, single-rim, double-rim or finely ridged borders. About 80% of parameter families inherit that border; the remaining families vary together. Circles stay circular; most other profiles stay nearly square, with elongated shapes a rare exception. Manufacturer counts influence depth. Border geometry is cached with the control face. Model and wiring hashes refine these traits within that family. Source-module and normalized parameter names retain related shapes; numeric variants receive only subtle shade differences. Palette selection remains derived, but the current panel skin and newly generated cables are rendered in grayscale. Existing cable colors are preserved. Jack art uses cached private grayscale copies, leaving the shared components unchanged. Cached faces retain native Rack interaction and mapped parameter identity. Discrete quantities use dots and ticks. Large shared captions wrap at whitespace only, never within words. The planner reserves the measured longest-word width; label fitting is cached per layout. Final clipping uses no ellipses. Styles are derived rather than saved separately.

`BeekapooSection.hpp` generates section backgrounds from the same structural hashes and a stable section role. Profiles include straight plaques, rounded plaques, clipped polygons, unequal polygon corners and symmetric clipped plaques. All sections have a single solid exterior with no internal seam. Each retains the existing perspective and grayscale section shading. Outlines are cached until geometry or identity changes; control placement and interaction bounds stay independent.

## Lettering

`ComputerscareTypeface.hpp` uses the bundled Computerscare Text face for labels,
buttons and numbers, and Computerscare Display for titles. Both are derived
from OFL-licensed Barlow, with 523 characters and four deterministic outlines
per character. `scripts/fonts/profiles.json` controls distortion; `build.py`
reuses the SVG lettering generator and writes the fonts and glyph mapping.
The supplied fonts build without Python/font-tool dependencies.

NanoVG does not select OpenType alternates, so cached display strings map each
character to a private-use glyph. These strings never enter saved names or the
clipboard. Whitespace and unsupported Unicode remain unchanged. Related labels
use the counted module hash; drawing and measurement use the same outlines.
Each alternate has the same advance width. The native rename field uses the
font's ordinary Unicode mapping, with the same font scoped around drawing and
mouse hit testing. Other modules keep their original fonts.

The normal check validates every glyph using Rack's font rasterizer. Native
font previews exercise both faces and both themes. Font licenses and build
instructions are in `res/fonts/computerscare/`.

## Patch planning and input routes

Port connection rules live in `res/Beekapoo/patch-rules/<plugin-slug>.json`, one file per manufacturer/plugin with entries keyed by module slug. `version: 1` defines `inputs`, `outputs` and optional `preferredOutputs`. Port keys and references are numeric Rack IDs. **`label` is an optional human-readable annotation only. It is ignored by generation, does not need to match Rack's label, and changing or removing it has no effect on behavior.**

`requiresInputs` and `requiresOutputs` are arrays of groups: OR within each group, AND between groups. Inputs may require connected inputs and used outputs; outputs may require connected inputs. A used output is connected onward or exposed. Empty rules have no requirements; an absent module profile uses the existing fallback. Declared ports are the participating port inventory (removed/unused ports can be omitted). The initial Fundamental inventory preserves the previous output choices. `preferredOutputs` is a flat list of equally preferred output IDs, used before other outputs; Grow can use the other outputs after the preferred outputs have been used.

`scripts/generate-beekapoo-port-rules.py` validates references, groups and input dependency cycles, then generates `src/BeekapooPortRules.inc`. The Makefile regenerates it on rule changes; `scripts/dev.sh check` verifies it is current. These are bundled build-time rules, not a user override loader. Changing JSON requires rebuilding. The generated C++ table needs neither Rack nor a JSON parser at runtime. No signal types or parameter settings are stored in this format.

`BeekapooPatchCatalog.hpp` keeps the separate generation policy: parameter exposure conditions, initial parameter ranges and curated candidate inputs. VCA Mix prefers Mix and exposes only useful channel CVs/levels. VCO/LFO PWM requires Square. Required input groups are connected before a processor is used, including transitive input prerequisites. ADSR's Gate input still must be connected, but the source is unrestricted. Signal-type filtering and envelope-specific construction have been removed from both generation and Grow. Existing strong modulation depths and useful starting levels are preserved.

`BeekapooPatchPlanner.hpp` is standard C++11 with no Rack, JSON, engine, or UI dependencies. `Planner(seed).make(count)` returns module indices, cables, exposed inputs/outputs, and parameters. `validate()` rejects missing prerequisites, ineffective controls and modules with no path to an exposed output. The tests cover 10,000 seeds, all mixer channels, square-only controls and deliberately broken dependencies. This follows RF2 rpatch's connected-graph approach, adding port-level prerequisites for Rack's Fundamental catalog.

`BeekapooGenerator.hpp` is the Rack adapter: instantiate the planned modules, apply catalog ranges, serialize the portable group, and assign cable colors. No graph decisions run in DSP. `BeekapooGrowth.hpp` mutates the existing native graph with native module/cable history; module IDs survive growth. It skips locked module endpoints.

`BeekapooInputRoutes.hpp` leaves new ordinary inputs as aliases of their original native jack, exactly like outputs: no multiplication, extra cable or DSP hop. Existing saved routes retain their IDs, parameters and gains for patch/MIDI compatibility; the removed attenuverter widgets are never created. Imported shared inputs still use native bridge routes to fan a single input out to several destinations and preserve capture silence. Only active legacy/shared routes are processed, in SIMD groups of four. Native cable ownership must be detached before calling `CableWidget::setCable` on the same cable: that setter deletes any cable it already owns.

`MappedParam::initParamQuantity()` deliberately does nothing. Initializing a second native Knob/Switch would mutate the original quantity's smoothing, snapping, reset and randomization policies. Source parameter IDs and quantities are shared; exposure is presentation only. `BEEKAPOO_EXPOSURE_STATE=1` tests values, quantity policies, MIDI handles, exact cable endpoints, immediate polyphonic signals, and repeated section add/remove/reroll actions.

`BeekapooButton.hpp` derives four-sided button proportions, corner offsets, perspective depth and border weight from the parameter family, source module and patch hashes. Related controls share their generated style. `ComputerscareContrast.hpp` chooses one border ink for the entire button. It prefers a dark outline when the main face remains readable against it; the face itself can supply the silhouette against a dark panel. Otherwise it balances contrast against the raised/recessed face and section background, with a soft-gray brightness ceiling. Dark bevels do not force light outlines. Choices are cached on theme/layout changes. The thin connected edge network draws after all fills, with the same ink in raised and recessed states. Text uses the stronger black/white contrast and fits its measured glyph bounds to both the width and height of the face. `BEEKAPOO_BUTTONS_ONLY=1` renders a light/dark button spectrum and checks both states for clipped glyphs and disconnected corners.

`BeekapooLabels.hpp` contains explicit short forms, including both "high pass" and "highpass" spellings. Rendering tries full text first, then a recorded abbreviation, and never splits a word or draws a partially clipped label. Full tooltips remain unchanged.

`BeekapooCompactLayout.hpp` plans narrow sections in standard C++ without Rack. The physical minimum reserves tiny jacks and usable parameter controls, not captions or the removed input attenuverters. Port rows compress in stages; captions disappear only when their actual cell cannot fit them. The Rack adapter supplies the header/action height and places the resulting sections. `BEEKAPOO_COMPACT=1` exercises minimum widths, mixed buttons/knobs, light/dark controls, non-overlap and source-state preservation.

On regeneration, `BeekapooPortable.hpp` snapshots both ends of panel cables by exposed input/output ordinal. This includes self-patches, duplicate stacks and wires completed immediately before Generate. Internal-only cables are replaced with the graph; panel slot connections and colors survive replacement, Undo/Redo and patch reload.

Selection merging lives in `BeekapooCreateSelection.hpp`. It flattens selected owners through Eject history, then captures the released native modules as one group. `scripts/preview/beekapoo-combine.hpp` exercises stacked sources, loopbacks, inter-group cables, gains, and atomic Undo/Redo. `beekapoo-placement.hpp` covers absolute Rack coordinates, Grow during editing, saved separated rows, and Eject placement. Set `BEEKAPOO_RECOVER_PATCH` to a copied patch JSON to inspect only its contained modules in the isolated renderer.

`BeekapooMemberLayout.hpp` packs changed membership into contiguous, balanced rows without moving modules during manual dragging. `BeekapooSectionAdd.hpp` handles the three section hover buttons and native exposure history; top-level Grow changes cables or adds a module from the selected set, favoring a VCA when available. Native member panels establish their layout before their first jack is relocated, so first-step layout caches never capture collapsed-panel positions.

## Exposed ports

Shared/legacy input bridges preserve polyphony. New ordinary ports use the original native endpoints. Eject uses Fundamental 8vert only for legacy non-unity gains or silence required by imported hardware capture.

`BEEKAPOO_POLYPHONY=1` checks native mono/poly routing, normalization, attenuation, Eject and Undo/Redo.

Input/output cells reserve captions before choosing jack size. `BeekapooLabels.hpp` supplies progressive phrase, word, numbered and compact alternatives; full port names remain in native tooltips. See [compact labels](beekapoo-labels.md) for the library survey and rule families. `BEEKAPOO_LABELS=1` renders real compact panels and checks caption visibility.

Whole-patch regeneration passes the current exposure counts to the standalone
planner. It chooses useful ports and parameters, adding module capacity if
needed; an unsatisfied plan leaves the existing subpatch intact. Fresh browser
creation retains its usual defaults. Structural edits refresh generated names
from the internal topology; restore establishes a baseline so saved/custom
names and history survive. Exterior cables and parameter values do not rename.

The header logo accepts both ordinary modules and other Beekapoos. Absorption
uses the native Eject transactions, retains the destination owner, restores
exposed gains/locks and groups the complete operation in one history action.

Module sets live in the Rack user directory as `computerscare-beekapoo-sets.json`. `BeekapooModuleSets.hpp` stores stable IDs, names, membership and the default for newly constructed modules. Each Beek serializes `generationSet`; legacy patches choose Fundamental. Missing entries are retained, and deleted set IDs fail generation until the user chooses another set. `BeekapooModuleSetEditor.hpp` is the Edit toolbar's compact brand/model browser. Global edits apply immediately; per-module set selection supports Rack Undo.

`BeekapooGenerationCatalog.hpp` adapts selected installed models to the standalone planner. The existing Fundamental rules take precedence; other models infer minimum signal/gate inputs from tags and port names and retain their default parameter values. Inference is cached per model and runs only on the UI thread. Generate and Grow share this catalog; Grow can add cables between existing members regardless of set, but adds only models from the selected set. No global set reads, model inspection or planning occur in the audio callback.

`BEEKAPOO_MODULE_SETS=1 scripts/preview-module.sh beekapoo --no-build` checks global persistence, missing models, defaults, patch serialization, restricted generation/growth, native history, and editor clicks/search/Escape, then renders the set editor. It uses only the renderer's scratch user directory.

## Cable membership and presentation

`BeekapooCablePresentation.hpp` resolves exposed input proxies to their child endpoints before deciding whether a connection is internal or belongs on the panel. It updates each native cable and both plugs together. Input attenuation is recorded separately from panel visibility (`attenuatedCables` versus `panelCables`); older saved groups are migrated without removing real connections. A hidden source cannot leave a visible plug in the rack.

`MergedControls` is shared by logo absorption and Create Beek-A-Poo. It captures mappings, gains, locks, and cable intent before owners are removed. Presentation repair waits until the topology transaction is complete, including Undo/Redo. Adding an ordinary upstream module retains a non-unity input gain rather than bypassing it. Disconnect cables leaves hidden attenuated routes intact.

`BEEKAPOO_CABLE_STATE=1 scripts/preview-module.sh beekapoo --no-build` checks both merge directions, two/three owners, repeated source stacks, self/cross-owner wiring, native endpoint identities, both plugs, signal values, Edit/Near/Far, Eject, Undo/Redo, and native patch reload. `BEEKAPOO_MERGE_PATCH=/path/to/patch.json` additionally checks a local reproduction, excluding audio interfaces and unrelated plugins.
